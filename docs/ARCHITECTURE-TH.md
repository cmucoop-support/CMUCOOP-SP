# สถาปัตยกรรมและการจัดเก็บ

## ขอบเขตการปรับโครงสร้าง

HTML เหลือโครงหน้าและการอ้างอิงไฟล์ ส่วน JavaScript/CSS อยู่ใน assets แยก shared/pages ทำให้แก้ไขแต่ละระบบได้โดยไม่ต้องเปิดไฟล์ HTML ขนาดใหญ่ ฟังก์ชัน pageUrl ที่เดิมซ้ำ 6 หน้าอยู่ใน shared/page-url.js แห่งเดียว

worker/index.js เป็น entry point ที่คงที่และส่งออกส่วนที่ชุดทดสอบใช้ ส่วนลงทะเบียน RPC ใช้ registry กลาง แต่ละระบบลงทะเบียนชื่อเดิม จึงไม่ต้องเปลี่ยนสัญญา google.script.run ของหน้าเก่า core/database.js เป็นจุดเดียวของการเขียนแบบ batch/chunk และตรวจ revision

คงตารางเดิมทั้งหมดและ migration 0001–0003 ไว้ ข้อมูล stock_data และสำเนาบาร์แบบเก่ายังคงอ่านและย้ายได้ตามเดิม ไม่มีการลบข้อมูลผู้ใช้จริงออกจากชุดโค้ด

## การอ่านและเขียน

- KV ขนาดใหญ่แบ่ง chunks และเขียน marker กับ chunks ใน transaction เดียว ปฏิเสธข้อมูลเสียหายหรือ chunks ขาด
- stock เก็บข้อมูลแยกกลุ่มและฉบับ มีการอ่านแบบ bulk และรวมคำสั่ง SQL ผ่าน json_each
- market ใช้ revision ป้องกันการบันทึกทับจากหน้าเก่า อ่าน marker กับ chunks ใน snapshot เดียว
- ผู้ใช้ stock ส่ง barcodeRevision ที่แคชไว้ ถ้าไม่เปลี่ยนจะไม่ส่งบาร์สินค้าทั้งหมดกลับมา และยังรองรับ client เก่าที่ไม่ส่ง revision
- market เขียนแบบร่างหลังหยุดแก้ 250 ms; flush ก่อนบันทึก/ออก/ซ่อนหน้า และตรวจเจ้าของแบบร่าง
- API shim รวมคำขออ่านที่เหมือนกันระหว่างรอผล จำกัดคำขอพร้อมกัน และไม่ลองบันทึกซ้ำอัตโนมัติหลังเน็ตขาดแบบไม่ทราบผล

## ทะเบียนสินค้า

`product_catalog_state` เก็บ revision ต้นทาง/revision ที่จัดทำทะเบียนแล้วและเวลาล่าสุด `product_catalog` เป็นแถวสินค้าต่อสาขา `product_catalog_records` เป็นรายละเอียดอ้างอิงจากแต่ละระบบ แยกรายการกับรายละเอียดเพื่อลด payload และแบ่งหน้ารายละเอียดจำนวนมากได้

เมื่อ source batch เปลี่ยนข้อมูล จะเปิด batching flag ปิดการเพิ่ม revision จาก trigger ทีละแถว แล้วปิด flag และเพิ่ม revision ครั้งเดียวใน transaction เดียวกัน การนำเข้า 2,000 แถวจึงเพิ่มตัวบอกการเปลี่ยนแปลงเพียงครั้งเดียว หากล้มเหลวทั้ง flag และข้อมูลย้อนกลับพร้อมกัน SQL ที่แก้ตารางต้นทางตรง ๆ นอก helper ยังมี trigger ตรวจการเปลี่ยนแปลง

sync อ่านข้อมูลต้นทาง ทำ projection ของข้อมูลสินค้าที่ต้องใช้ แล้วเทียบกับทะเบียนเดิมเพื่อเพิ่ม/แก้/ลบเฉพาะแถวที่เปลี่ยน ถ้าข้อมูลต้นทางเปลี่ยนระหว่างสร้าง SQL CHECK จะยกเลิกการเผยแพร่ทั้งชุดและลอง snapshot ใหม่ การอ่านทะเบียนตรวจ marker ใน snapshot อีกครั้งเพื่อไม่คืนข้อมูลเก่าที่เกิดจากการบันทึกคั่นระหว่าง sync กับ read

ข้อมูลอนุพันธ์ไม่ใช่แหล่งข้อมูลหลัก การแก้สินค้าให้แก้ที่ระบบต้นทาง การลบหรือเปลี่ยนข้อมูลต้นทางจะปรับรายการและแหล่งอ้างอิงในทะเบียน โดยเก็บแหล่งอื่นที่ยังมีสินค้าอยู่ หากสต็อกขาดทั้งกลุ่มหรือ chunks ขาด จะปฏิเสธการสร้างทะเบียนใหม่และคงฉบับที่เผยแพร่ไว้

มีการยุบการเรียก sync พร้อมกันภายใน isolate และตรวจ revision ในฐานข้อมูลเพื่อป้องกันการชนข้าม isolate แบ่ง JSON สำหรับทะเบียนไม่เกิน 1,800,000 ไบต์ต่อพารามิเตอร์ โดยตัวช่วยคำนวณขนาด UTF-8 จริง ฟิลด์ sourceKey สร้างกลับตอนอ่านรายละเอียดแทนการเก็บซ้ำใน JSON

บาร์ข้อมูลกลางแสดงแยกจากสาขา ส่วนรหัสที่ตรงกันช่วยเชื่อมรายละเอียดไปยังสินค้าของสาขานั้น ชื่อจาก stock มีลำดับหลัก ตามด้วย market, expiry, barcode แต่ยังแสดงชื่อที่แตกต่างและแหล่งอ้างอิงทั้งหมด ไม่รวมสินค้าจากชื่ออย่างเดียว และไม่บวกจำนวนคนละระบบเข้าด้วยกัน

## ข้อจำกัดที่ต้องตรวจใน staging

การซิงก์ที่พบการเปลี่ยนแปลงยังต้องอ่านและเทียบ projection ของข้อมูลต้นทางเพื่อคงความถูกต้อง จึงไม่ใช่ zero-cost หรือการรับประกันขนาดข้อมูลไม่จำกัด รอบที่ข้อมูลไม่เปลี่ยนข้ามการอ่านต้นทางและไม่เขียนแถวสินค้าใหม่ การค้นหาคำบางส่วนใช้ SQL instr เพื่อค้นหาอักขระพิเศษแบบ literal ส่วนการกรองสาขาและแบ่งหน้าใช้ดัชนี

ทดสอบข้อมูลจำลอง 30,000 รายการในเครื่องได้ แต่โควตาและ CPU ของ D1/Workers จริงขึ้นกับแผนบริการ ปริมาณหลายระบบรวมกัน และการบันทึกพร้อมกัน การสร้างทะเบียนครั้งแรกหลังนำเข้าชุดใหญ่อาจต้องซ่อมต่อเมื่อเปิดทะเบียน หากการซิงก์ในคำขอบันทึกใช้ทรัพยากรเกินขีดจำกัด ข้อมูลต้นทางที่ commit แล้วไม่ถูกบันทึกซ้ำโดยอัตโนมัติ
