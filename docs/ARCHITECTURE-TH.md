# สถาปัตยกรรมและการจัดเก็บ (ฉบับประหยัดโควตาการเขียน D1)

## ขอบเขตการปรับโครงสร้าง

- ตัดระบบการ์ดทะเบียนสินค้า (`catalog.html`, `catalog.js`, `catalog-sync.js`, ตาราง `product_catalog*` และ SQLite Triggers `catalog_dirty_*`) ออกทั้งหมด เพื่อไม่ให้ทุกการบันทึกสต็อก บาร์โค้ด ตลาด และวันหมดอายุต้องเขียนตารางอนุพันธ์ซ้ำหลายหมื่นแถว
- คงตารางหลักของระบบเดิมทั้งหมดไว้ และลบตารางอนุพันธ์รวมถึง Trigger ที่ไม่ใช้แล้วอัตโนมัติใน `ensureSchema`

## การลดจำนวนแถวที่เขียนลง D1 (Row Writes Optimization)

1. **KV และ Chunks (`core/database.js`)**:
   - ใช้เงื่อนไข `ON CONFLICT(k) DO UPDATE SET v=excluded.v WHERE kv.v<>excluded.v` และ `WHERE kv_chunks.data<>excluded.data` เพื่อไม่ให้ SQLite นับ Row Write เมื่อข้อมูลเดิมไม่เปลี่ยนแปลง
   - ขยายขนาดก้อนข้อมูล (`kv_chunks`, `stock_grp`, `market_data`) เป็น 240,000 ตัวอักษรต่อก้อน ลดจำนวนแถวที่ต้องเขียนลง 3 เท่า
2. **รายการบาร์สินค้า (`modules/barcode.js`)**:
   - การนำเข้าแบบแทนที่ (`importBarcodeData` / `barcodeRestore`) เทียบข้อมูลเดิมกับข้อมูลใหม่ทีละตำแหน่ง เขียนเฉพาะแถวที่เปลี่ยนและลบเฉพาะแถวส่วนเกิน โดยไม่ผ่านตารางพัก `barcode_stage`
   - สำเนาข้อมูลบาร์ (`bcSnapshot`) เก็บเป็นก้อน JSON และตรวจค่าแฮช SHA-256 ก่อนสร้างสำเนาใหม่
   - การเพิ่มรายการ (`addItem`) เลื่อนลำดับเฉพาะในหมวดเดียวกันเมื่อระบุคู่ค้า ไม่เลื่อนแถวข้ามหมวดทั้งตาราง
3. **แจ้งเตือนสินค้าหมดอายุ (`modules/expiry.js`)**:
   - ดัชนีค้นหาชื่อและรหัสสินค้าจากสต็อกถูกสร้างและแคชในหน่วยความจำของ Worker ตาม `revision` ของสต็อก (เขียนลง D1 เป็น 0 แถว)
4. **คิวเพลงและหน้าจอรับสัญญาณ (`modules/music.js`)**:
   - บันทึก `MUSIC_PROG` เฉพาะเมื่อเปลี่ยนเพลง เปลี่ยนสถานะ หรือเวลาคลาดเคลื่อนเกิน 4 วินาที และอัปเดต `MUSIC_TV_SEEN` ไม่เกินทุก 45 วินาที
5. **การเข้าสู่ระบบและประวัติการใช้งาน (`modules/auth.js`, `core/logging.js`, `modules/portal.js`)**:
   - ล้างประวัติเก่าเกิน 30 วันเพียงวันละ 1 ครั้ง และไม่บันทึกประวัติเมื่อผู้ใช้เพียงแค่คลิกเปิดการ์ด สลับแท็บ หรือเลือกหมวด
   - รองรับ Stateless Signed Token (`s1.`) อัตโนมัติหาก D1 ติดขีดจำกัดการเขียนรายวัน เพื่อให้ยังเข้าสู่ระบบและดูข้อมูลได้ต่อเนื่อง
